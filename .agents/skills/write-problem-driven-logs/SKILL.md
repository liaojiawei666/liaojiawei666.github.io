# 问题驱动日志写作

## 强制流程

处理新话题或新增主要章节时，必须先讨论写作脉络，不得直接写正文。先输出：

```text
核心问题：
一句话结论：
目标读者：
叙事入口：
问题链：
贯穿例子：
章节顺序：
暂时不写：
需要的图：
需要核实的事实：
```

等待用户确认后再写正文。只有用户明确要求“直接写”时才跳过讨论。局部改字、删段或修正事实时，不要重新讨论整篇脉络。

## 结构讨论

1. 把技术文章组织为“问题 → 原理 → 应用”：先说明技术为什么出现，再解释核心方案为什么成立，最后说明如何落地及其边界。
2. 与用户讨论文章结构时，把主线回答为“问题 → 核心解决方法 → 由此产生的新问题 → 新的核心解决方法”；把不产生后续问题的独立内容回答为“独立问题 → 核心方案”。新问题必须由前一方法自然产生，不得为套用结构而生造问题。

## 写作规则

1. 一篇文章只回答一个核心问题。删除不能帮助回答该问题的内容。
2. 开头先给结论，再说明主题解决什么问题以及为什么值得了解。
3. 按“原来的办法 → 遇到的问题 → 新办法 → 工作原理 → 具体例子 → 使用边界”组织内容，不按术语分类堆砌。
4. 先说明需要解决的问题，再引入对应概念或术语。
5. 先用通俗语言建立直觉，再给出准确术语；不要用比喻代替正式定义。
6. 使用一个贯穿全文的例子，保持人物、数据和场景一致。
7. 每个小节只回答一个问题；每个段落只表达一个意思。
8. 使用短句和直接因果关系。只提出会立即回答的真实疑问。
9. 公式和代码出现前说明用途，出现后解释结果。禁止连续堆放未解释的公式或大段代码。
10. 图片只回答一个明确问题。信息传递优先画人物与信息变化；只有复杂系统关系才画架构图。
11. 只保留理解主线所需的历史、证明和实现细节。
12. 只说明最重要的误解、限制和失败条件，不扩写无关边界。
13. 核实安全参数、标准、软件行为和行业现状等会变化的事实，优先使用一手资料并就近引用。
14. 删除套话、重复结论、装饰性类比、空泛评价和没有信息量的过渡句。
15. 核心问题回答完毕后立即停止，不重复全文。

## 完成前检查

逐项检查；任意一项不满足时，先修改再交付：

- 开头是否直接回答核心问题？
- 每个概念出现前，读者是否已经知道为什么需要它？
- 每节是否只回答一个问题？
- 贯穿例子是否前后一致？
- 公式、代码和图片是否都帮助理解？
- 是否存在未经核实的时效性事实？
- 删除任意一段是否不影响理解？如果不影响，删除该段。
- 结尾是否在答案完整后立即停止？
